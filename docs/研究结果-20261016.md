## 假设、实验与结论

### 历史迭代：默认请求头缺陷与分类要求

- **已确认缺陷**：yt-dlp初始化时会把默认请求头写入`YoutubeDL.params['http_headers']`，原下载探针覆写`urlopen`后只传递单次`Request.headers`，遗漏上游合并步骤。真实BiliBiliIE第一次网页请求的单次头为空，因此User-Agent、Accept、Accept-Language、Sec-Fetch-Mode没有传入；urllib会使用自己的默认User-Agent。这是自有探针缺陷，尚不能据此认定它是HTTP412的唯一原因。
- **失败复现**：新增测试通过真实`download_one → BiliBiliIE → ResearchYDL → BoundedTransport`路径，在urllib边界截断。禁止socket/DNS、凭据读取及子进程；合成空Cookie不接触账号。旧代码结果为2项失败、47项通过，失败分别揭示默认User-Agent及默认Referer丢失；原始失败XML保留。
- **修复范围**：恢复固定版本的`HTTPHeaderDict(默认头, 单次请求头)`语义，按不区分大小写的规则让单次请求覆盖默认值，然后继续过滤Cookie、Authorization、Proxy-Authorization并固定Accept-Encoding=identity。代理、版本、Cookie来源、重定向、请求预算和超时不变。该修复不是切换身份或指纹反复试探。
- **正常浏览器前提**：当次使用已连接的普通Edge浏览器只打开一次固定视频页，观察到对应标题和播放器00:06/09:14，随后关闭临时标签页。未读取/迁移Edge凭据，未记录账号资料、跟踪参数或完整页面；只保存结构化观察记录。浏览器的资源请求数及HTTP状态没有测量，其会话不等同专用Chrome探针会话。
- **证据边界**：不同传输实现仍有代理配置、压缩及Cookie容器等差异；当次仅修复已确定的默认头合并问题。页面验证、真实媒体、完整动态索引和产品人工验收分别判断，不能通过离线测试推断线上成功。
- **分类要求**：已登记“作者 → 图文／图片、投稿视频、动态视频、待分类 → 作品”，并补充R06/F08验收。实况的配套MP4仍属于图片组；BV、扩展名或动态发现入口不能直接决定类别；同BV/CID只保留一份资源，多入口关联；转发身份分开保存。当前只是需求和待验证契约，没有产品分类器或目录迁移。

**当次在线结果**：2026-10-16 19:27（Asia/Shanghai），预注册单页探针首先通过nav实际登录检查，然后固定视频页面返回HTTP301。探针未跟随重定向，累计2次请求、0媒体，立即结束；没有进入视频提取、合并或多P下载。证据只记录状态码，没有保留Location，因此当时重定向目标及其规则尚未核实。不能把301当作页面PASS，也不能把与旧412不同的结果归因于请求头这一项；浏览器、时间与传输条件并非受控等同。下一项需单独研究原站规范URL与重定向规则，再登记有界验证；当轮不追加B站请求。

当轮实际文件：`video_download_probe.py`的默认头合并与调用接线；`video_page_probe.py`的独立两请求验证；对应新增29项合成测试。首轮修复的导入错误已改正，没有通过忽略失败测试获得通过。源码提交`9bc21d6a36b259a899e34a71f42b073b2bae0976`已推送，其[Windows CI](https://github.com/awa606/BiliBatchDownloader/actions/runs/38894318400)在Python3.13.16通过204项测试，耗时6.35秒；后续文档补记不冒充新的源码验证。

研究探针超时会保留中断文件并标BLOCKED，但视频探针没有逐资产运行中持久化进度。超时报告不代表零媒体或准确的已执行请求数；只有本轮实际返回的412报告及目录检查证明该次没有媒体。产品级重启恢复队列尚未实现。
